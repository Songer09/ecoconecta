# Seguridad de software — baseline 2026/2027

**Objetivo:** aplicar controles modernos y verificables. Ninguna lista garantiza seguridad absoluta. El nivel de exigencia debe adaptarse a los datos, exposición y riesgo reales del MVP.

## 1. Referencias de trabajo

- OWASP Application Security Verification Standard (ASVS) **5.0.0**, estable: https://asvs.owasp.org/
- OWASP Top 10 **2025**: https://top10.owasp.org/2025/
- OWASP API Security Top 10 **2023**: https://owasp.org/www-project-api-security/
- NIST Secure Software Development Framework (SSDF), SP 800-218: https://csrc.nist.gov/pubs/sp/800/218/final

Revisar versiones oficiales al iniciar una nueva fase; no afirmar que existe una versión 2027 si aún no ha sido publicada. ASVS es una base verificable, Top 10 es concienciación y SSDF organiza prácticas de desarrollo seguro; no son certificación automática.

## 2. Modelo de amenazas mínimo

Proteger:
- teléfonos, nombres, direcciones y referencias de ubicación;
- cuentas, credenciales y sesiones;
- solicitudes, asignaciones y agenda;
- puntos y registros de recolección;
- imágenes y metadatos;
- tokens de proveedores y webhooks;
- reportes/exportaciones.

Amenazas:
- acceso horizontal a solicitudes de otras personas/zonas;
- elevación de privilegios;
- abuso de cuentas de coordinador/admin;
- enumeración de IDs;
- inyección SQL/XSS/CSRF/SSRF;
- robo de sesión/token;
- webhook falsificado/replay;
- doble procesamiento de eventos;
- carga de archivos maliciosos;
- prompt injection y salida insegura de IA;
- exposición de secretos en repositorios, logs o artefactos;
- dependencias comprometidas;
- abuso/denegación de servicio.

## 3. Identidad y sesiones

- Usar librería/mecanismo mantenido; no implementar criptografía propia.
- Contraseñas con Argon2id (parámetros actuales recomendados por OWASP) o delegar autenticación en proveedor confiable; nunca cifrar contraseñas reversiblemente.
- MFA para administradores/coordinadores privilegiados cuando sea viable.
- Rate limiting y protección frente a credential stuffing.
- Respuestas de login que no revelen si una cuenta existe.
- Sesiones revocables, expiración razonable y rotación de refresh tokens si se usan.
- Cookies de sesión: `HttpOnly`, `Secure`, `SameSite` adecuado; protección CSRF si auth por cookie.
- Tokens: no almacenarlos en `localStorage` si se puede usar cookie segura; si se adopta otro patrón, documentar amenaza y mitigación.
- No registrar credenciales, tokens ni encabezados Authorization.

## 4. Autorización

- Denegar por defecto.
- RBAC + comprobación por objeto y ámbito (usuario, zona, solicitud, rol).
- Comprobar permiso en cada endpoint y acción, incluidas descargas, exportaciones y consultas.
- Evitar confiar en IDs enviados por cliente.
- No usar roles/claims del frontend como autoridad.
- Separar administración de usuarios, reglas de puntos y operación cotidiana.
- Probar expresamente que un usuario no puede leer/modificar solicitudes de otro.

## 5. API y datos

- Validación estricta Pydantic y límites de longitud/tamaño.
- ORM/consultas parametrizadas; nunca concatenar SQL con input.
- CORS con allowlist exacta; no `*` con credenciales.
- HTTPS obligatorio en despliegue.
- Rate limits por usuario/IP/operación; límites más estrictos para login, carga y webhooks.
- Paginación y límites máximos; evitar consultas masivas.
- Mensajes de error sin stack trace ni datos internos.
- Cabeceras de seguridad adecuadas; CSP para frontend según arquitectura.
- Control de caché para datos privados.
- Protección CSRF si se usan cookies.
- Validar URLs/hosts cuando el servidor realiza peticiones externas para reducir SSRF.

## 6. Privacidad y ciclo de vida

- Minimizar datos recolectados y compartidos.
- Separar información de contacto/ubicación de vistas operativas cuando sea posible.
- Mostrar al recolector solo lo necesario para su asignación.
- No enviar datos personales a IA si no es imprescindible.
- Definir finalidad, base legal/consentimiento aplicable, aviso de privacidad, responsable, retención y procedimiento de eliminación con la Fundación.
- Cifrado en tránsito; cifrado en reposo gestionado por infraestructura/BD cuando esté disponible.
- Backups cifrados, acceso limitado y pruebas de restauración.
- No usar datos reales en entornos de desarrollo, demos públicas o datasets sin autorización.
- No publicar coordenadas/direcciones en reportes abiertos.

## 7. IA y reconocimiento

- IA no toma decisiones finales de asignación, cierre o puntos.
- Validar entradas y limitar tamaño/tipo.
- Tratar imagen, texto y metadatos como contenido no confiable.
- Prevenir prompt injection: el contenido del usuario nunca debe poder cambiar instrucciones del sistema ni invocar herramientas arbitrarias.
- No dar al modelo herramientas con privilegios amplios.
- Validar salida contra esquema; no ejecutar código/SQL generado por modelo.
- No confiar en salida del modelo como autorización.
- Registrar modelo/versión y resultado de forma minimizada.
- Evaluar sesgos, errores por clase y abstención.
- Tener fallback manual cuando IA falle o no esté disponible.
- Si un proveedor externo procesa imágenes o datos personales, aprobar contrato, ubicación, retención y condiciones antes de enviar.

## 8. Archivos e imágenes

- Allowlist de formatos; validar MIME y firma.
- Límites de bytes, dimensiones, duración y cantidad.
- Nombres aleatorios; almacenamiento privado fuera del webroot.
- Eliminar EXIF/GPS.
- No ejecutar contenido subido.
- Analizar/aislar archivos cuando sea posible.
- URL firmada de expiración corta si se usa object storage.
- Autorización por objeto al descargar.
- Política de borrado y retención.

## 9. Webhooks y eventos

- Verificación criptográfica según proveedor.
- Timestamp/nonce cuando el proveedor lo soporte para mitigar replay.
- ID de evento único con constraint de base de datos.
- Idempotencia y procesamiento transaccional.
- Cola/reintentos solo si están aprobados y se justifican; no añadir Redis por defecto.
- Separar recepción del webhook y ejecución de procesos pesados.
- No confiar en el orden de llegada.
- No aceptar eventos de remitentes no verificados.

## 10. Seguridad de la cadena de suministro

- Dependencias fijadas con lockfiles.
- Evitar paquetes abandonados y dependencias innecesarias.
- Escaneo de vulnerabilidades/SCA en CI.
- Secret scanning en commits y repositorio.
- SBOM para release si el tiempo/infraestructura lo permite.
- Imágenes Docker base mínimas, versionadas por digest para releases sensibles.
- Ejecutar contenedores como usuario no root.
- No montar Docker socket dentro de contenedores de aplicación.
- No incluir compiladores, shells o herramientas de debugging en imagen final sin razón.
- CI con permisos mínimos, secretos solo en jobs que los necesitan.
- Revisar cambios de dependencias y scripts de instalación.

## 11. Observabilidad y auditoría

- Logs estructurados, sanitizados y con correlation/request ID.
- No loguear teléfonos, direcciones, imágenes, contraseñas, tokens ni payloads completos.
- Auditoría de acciones privilegiadas, cambios de estado, asignaciones y puntos.
- No permitir que usuarios ordinarios alteren o borren auditoría.
- Alertar sobre fallos repetidos de login, permisos, webhook y errores críticos.
- Sin datos personales en métricas/traces.
- Definir retención de logs.

## 12. PostgreSQL

- Usuario de aplicación sin superuser/CREATEDB.
- Credenciales distintas por entorno.
- Red privada; no exponer puerto públicamente.
- TLS si conexiones cruzan red no confiable.
- Backups automáticos cifrados y prueba periódica de restore.
- Migraciones revisadas y plan de rollback.
- Constraints/transactions para puntos y recolección.
- Consultas parametrizadas y límites de tiempo.
- Separar usuario de migraciones del usuario runtime si el despliegue lo permite.

## 13. CI/CD y release

- PR obligatorio y revisión humana.
- Tests, lint, typecheck, SCA y secret scan como gates.
- No usar `continue-on-error` para pruebas que deben bloquear release.
- Artefactos reproducibles; proteger ramas y entornos.
- Secrets por entorno y rotación ante exposición.
- Despliegue con health checks y rollback.
- Separar staging/demo/producción.
- No promover a producción si existen vulnerabilidades críticas/altas sin excepción aprobada y documentada.

## 14. Checklist de salida

- [ ] Autorización por objeto probada.
- [ ] No hay secretos en Git ni historial reciente.
- [ ] Webhooks verificados e idempotentes.
- [ ] Operaciones de puntos atómicas y no duplicables.
- [ ] Carga de imágenes restringida y privada.
- [ ] Logs sanitizados.
- [ ] Dependencias escaneadas y lockfiles actualizados.
- [ ] Backups y restore verificados.
- [ ] HTTPS y configuración segura.
- [ ] Errores sin información sensible.
- [ ] IA tiene fallback humano y no ejecuta decisiones críticas.
- [ ] Aviso/retención de datos revisados por responsable.
- [ ] Evidencia de pruebas documentada.
